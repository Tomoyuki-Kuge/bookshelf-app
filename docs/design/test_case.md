## 読み方・確認の前提

- 対象・資料の優先順位は [README.md](README.md) に従う。手動の受け入れ条件は [acceptance.md](acceptance.md)、内部制約・API書き込み・テスト実行結果を含む詳細なテスト観点は本書で扱う。文書の記載はテスト実行済みを示さない。
- 12実装単位の並び順は受け入れ条件と共通とし、IDは `T-単位番号-連番`。テスト観点は「ID・何を確かめるか・区分・元になった設計書」の4列にまとめ、区分は正常系・異常系・境界値のいずれかとする。
- 組み合わせの全列挙やテストコードは記載しない。特記のない観点では確認対象以外の条件を有効な状態にし、各機能のテストはその実装単位、単位12は横断確認と不足分を扱う。
- Q-18・19・23・24・26とQ-22の回答状態は [questions.md](questions.md#未確定事項の確認先一覧) に従う。Q-18・22〜26はQAで回答済み、Q-19の正式認証文言と表示先は確定。ログインの入力エラーも登録と統一することを2026-11-22のユーザー回答で承認済み。未指定の個別文言は保留を維持し、認証の上限・重複等の暫定採用と区別する。**（※仕様保留中）** は確認対象の予約であり、未承認の想定案を期待値として採用しない。回答・開発側の決定を元の設計書と本書へ反映してから検証し、未確定項目を合格扱いにしない。

## 確認用データの準備

- 書籍一覧の自動テストは開始前の件数を基準に追加件数の差分を確認する。既存書籍と追加書籍のID・登録日時からPHP側で期待順を組み立て、10件ずつに分けた各ページのID列・総件数・ページ内件数を照合する。平均評価は今回作成した対象書籍で確認し、既存データを変更・削除しない（2026-11-20ユーザー承認）。

- 初回Seederの確認は指定データだけの状態で行う。5人・10ジャンル・11冊・32レビュー、お気に入り各3〜5冊、いいね各レビュー0〜3人の確認と、追加データを使う境界値・認可の確認を分ける。追加後の総件数を初回Seederの合否に使わない（[初期データ](features.md#初期データ)、T-3-1〜19）。
- 初期11冊の作成者は既存要件の `User::first()`（山田太郎想定）を維持する。Eなどを別作成者にする場合は、初期11冊を付け替えず、未使用ISBNの追加書籍をテスト用データとして用意する。ジャンルに作成者は割り当てない。
- Dのページ分割確認では、お気に入りを0・1・10・11件にするデータを用意する。書籍一覧・ジャンル内書籍は各対象の件数を別に調整し、レビューは10件を超えても全件表示されることを確認する。
- ランキングは平均の丸め差、同平均での件数差、同平均・同件数でのID順を計算できるデータを用意する。相互レビューや初期Seederだけで必要な同点条件が揃うと仮定しない。
- トグル確認前に対象利用者の登録状態と全体件数を揃え、0件表示・削除・複数ページなどの場面ごとに独立した状態を使う。同時操作はQ-23の直列化と受付ごとのトグル、解除後はQ-24の現ページ維持・消滅時の最終有効ページ補正を期待結果とする。

## 2. 既存画面への接続と認証

対応する受け入れ条件: [単位2](acceptance.md#2-既存画面への接続と認証)。

Issue #2の接続段階はpermissions-api.mdを参照する。T-2-9〜10のうち未接続の業務画面の描画・閲覧は後続で検証し、ルート登録と認証誘導だけで全範囲の合格にしない。ログイン試行制限の日本語表示、成功時の制限解除、セッション更新、不要な認証経路が未公開であることも検証する。

T-2-6・7・14・15の表示確認は実際のPOSTからリダイレクト後のHTMLまで検証する。ログインの認証失敗・入力不正、登録の入力不正・確認不一致を分け、DOMで対象入力欄と同じ親要素内の入力欄より後に文言があることを確認する。全パスワード欄（登録の確認欄を含む）のvalueは未指定または空とし、送信したパスワードがHTMLに含まれないことも確認する（2026-11-20ユーザー承認）。

接続段階の本人制限は、書籍・レビューのGET編集・PUT・DELETEを1リクエストずつ検証する。他人へのPUTには設計上有効な入力を送り、403の直前・直後でDBから本体・関連行を主キー順に再取得し、日時を含む全保存値を配列で厳密比較する。書籍にはジャンル・レビュー・お気に入り・いいね、レビューにはいいねを準備し、無関係な書籍・レビューと関連行の保持も確認する（2026-11-20ユーザー承認）。2026-11-23のユーザー指示により、書籍・レビューそれぞれのPUT・DELETEに攻撃者自身のuser_idを含めるケースも追加し、送信値を信頼せず403・全保存値不変となることを確認する。

登録のpassword・password_confirmationには配列も送信する。双方を同じ8要素配列にして、最低文字数や確認一致だけでは型不正を検出できないケースを含める。Bladeでは422のJSON応答を期待せず、元フォームへのリダイレクト・該当項目のセッションエラー・利用者未作成・パスワード非保持・フォーム再表示を確認する（2026-11-23ユーザー指示）。

削除済み対象の経路確認では、接続段階のWeb削除が501のためモデルで実際に書籍・レビューを削除して準備する。元の所有者でGET編集・有効な入力のPUT・DELETEを行い、各操作の404、削除済みIDの不存在、削除準備後を基準とした業務7表の全保存値不変を確認する。レビュー単独削除では親書籍を残し、別IDでの再作成や関連行の変更も検知する。Web削除成功の確認は単位6・7で行い、対象不存在と入力不正の優先順位は今回の期待値に含めない（2026-11-20ユーザー承認）。
