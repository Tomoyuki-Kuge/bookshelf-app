#### 任意項目の省略・null・空文字（レビュー項目1）

**【課題・未決事項】**

説明・画像URLを未入力にした場合の保存値と、更新APIで省略した場合に既存値を維持するかが未確定。画面で任意であることだけでは、DBのNULL可否やAPIから値を消す方法までは決まらない。

**【想定される影響・リスク（手戻りの大きさ）】**

DB定義、Web・APIの保存処理、Resourceの返却値にまたがる。省略を空値と同一視すると、変更するつもりのない説明・画像URLを消してしまう。後から変更するとスキーマと保存・入出力テストを修正する必要があるため、スキーマ実装前に方針を揃える。

**【開発側の推奨案（仮説）】**

| 入力 | POST | PUT |
|---|---|---|
| 項目を省略 | NULLで新規保存 | 既存値を維持 |
| null・空文字 | NULLで新規保存 | 既存値をNULLへ変更 |
| 有効な文字列 | 入力値で新規保存 | 入力値へ変更 |

対象を `description`・`image_url` の2項目に限定し、DBも両列をNULL許容にする案を推奨する。Webで空欄を送った場合もNULLへ統一し、未設定を空文字と二重管理しない。APIの省略と明示的な空値を区別することで、値の維持・削除を呼出側が選べる。PUTの必須項目をすべて要求する条件と、ジャンル集合を置換する条件は変更しない。

#### JSON構造・型・日時の表現（レビュー項目3）

**【課題・未決事項】**

ジャンルのパラメータ名、返却するキー・JSON型、レビューの配置・範囲、日時・平均評価の表現が未承認。現在のJSON例は構造を検討するための案であり、実装・テストの確定契約として扱えない。

**【想定される影響・リスク（手戻りの大きさ）】**

FormRequest・Resource・API利用側・契約テストが同じ表現に依存する。各実装で別々に決めると、一括修正が必要になる。特に日時のタイムゾーンや数値を文字列として返すかどうかは、表示・比較にも影響するためAPI実装前に確定する。

**【開発側の推奨案（仮説）】**

既存のAPI詳細案をまとめて採用し、Webの項目名と対応させる。API利用側が型や配置を推測せず扱えるよう、以下を契約として明記する。

| 対象 | 想定案（未承認） |
|---|---|
| キー・構造 | 入力ジャンルは `genres`、出力は `genres: [{id, name}]`、平均は `average_rating`、件数は `reviews_count`、投稿者は `user_name`。配列要素エラーは `genres.0` 等 |
| JSON型 | ID・件数・評価は整数、ISBN・出版日・本文は文字列。任意2項目は文字列またはnull、平均は数値またはnull。数値を表示用の文字列へ変換しない |
| 日付・日時・平均 | 出版日は時差変換せず `YYYY-MM-DD`、投稿日時はISO 8601・UTC・秒単位（例：`2026-11-18T00:00:00Z`）。APIの平均は小数2桁へ四捨五入した数値。未評価はnull・0件を維持。Webの表示桁数とランキングの未丸め比較は変更しない |
| 返却範囲 | 一覧は書籍・ジャンル・平均・レビュー件数。詳細は書籍・ジャンル・全レビューを登録日時降順、同日時はID降順で返す。POST・PUTは保存後の書籍・ジャンルとし、レビュー配列・集計を加えない |
| 包み・ページ情報 | 確定済みのdata・一覧links/meta・削除204本文なしを維持。links/metaのキー・型はpermissions-api.mdの案を採用し、0件・範囲外の値は次の検索・ページの案に揃える |
| APIエラー文言 | 422のmessage「入力内容に誤りがあります。」、404「書籍が見つかりません。」。項目別はQ-19と共通、不正なuser_id「指定したユーザーが存在しません。」、不正な検索ジャンル「指定したジャンルが存在しません。」 |
| 検索・配列の形式エラー | keywordはQ-19の文字数文型、page「ページ番号は1以上の整数で指定してください。」、per_page「1ページの件数は1〜100の整数で指定してください。」、genresの型不正「ジャンルは配列で指定してください。」。IDの型不正は「{項目名}は整数で指定してください。」、配列内の不正ID・重複はQ-19に合わせる |

エラーの `errors` は項目名をキー、メッセージ文字列配列を値とする。投稿者メール等の要件外の個人情報は返さない。`Accept: application/json` とPOST・PUTの `Content-Type: application/json` も詳細案として採用することを推奨する。APIでUTC表記を採ることだけで、DBの保存タイムゾーンや日時列の物理条件を決めたことにはしない。

#### 検索語と範囲外ページ（レビュー項目5）

**【課題・未決事項】**

検索語の前後空白、英字の大小、全半角、`%`・`_` の比較方法と、最終ページを超える正のページ番号の応答が未確定。空の結果で返すmetaや、ページリンクへ検索条件を引き継ぐ方法も未承認。

**【想定される影響・リスク（手戻りの大きさ）】**

DBの比較方法・検索条件の組立て・ページ情報・APIテストに影響する。`%`・`_` を検索用のワイルドカードとして扱うと、入力文字そのものを探した利用者の意図と結果がずれる。ページ移動で検索条件が落ちると、一覧の対象自体が変わる。

**【開発側の推奨案（仮説）】**

| 対象 | 推奨する挙動（未承認） |
|---|---|
| keyword | 前後空白を除去し、空なら検索条件なし。英字大小は区別せず全角半角は区別。`%`・`_` はワイルドカードにせず、通常の文字として部分一致させる |
| 条件・順序 | 確定済みの「タイトルOR著者」とジャンルのAND条件を維持。登録日時降順・同日時はID降順とする |
| ページ番号 | 省略は1。最終ページを超える正の整数は200＋空配列とし、有効ページへ自動補正しない。0・負数・非整数は422 |
| 検索結果0件 | page=1なら `total: 0`、`from/to: null`、`current_page/last_page: 1`、前後リンクnull |
| 範囲外のmeta | 要求pageをcurrent_pageに保ち、from/toはnull。last_pageは実際の最終ページ（全体0件なら1） |
| ページリンク | keyword・genre_id・per_pageの適用中の条件を引き継ぐ |

文字そのものを探す検索に揃え、存在しないページの要求も空の一覧として扱うことで、検索結果0件と同じ応答構造を保てる。比較・エスケープの具体方式は開発側で検討し、採用DBで確認する。検索の比較規則は新しい案であり、確定済みのジャンル名の比較規則を変更するものではない。Webのお気に入りのページ補正はQ-24で別に扱う。

### Q-18：更新APIによる登録者変更の可否

**未回答（※仕様保留中）。** レビュー項目2に対応。

**【課題・未決事項】**

PUTで現在の登録者と異なる実在 `user_id` を渡した場合に、登録者を変更するか、現在の登録者と一致するIDだけを受け付けるかが未確定。PUTの `user_id` 必須と、基本APIの認証・所有者制限なしはQA Q-03・07の確定条件であり、呼出人の本人確認とは区別する。

**【想定される影響・リスク（手戻りの大きさ）】**

API更新後のWebの編集・削除権限が変わる。保存する登録者とPolicy・画面の本人操作の判定が一致しないと、旧登録者と新登録者のどちらが操作できるか食い違うため、API更新と認可テストの実装前に確定する。

**【開発側の推奨案（仮説）】**

実在する指定 `user_id` への登録者変更を許可し、Webの編集・削除権限は保存後の `books.user_id` に従って新登録者へ移す。必須入力として指定する登録者と保存結果を一致させ、Webも現在の登録者で判定できるため、この案を推奨する。旧登録者は変更後のWeb更新・削除で403、新登録者は操作可能となる。

APIの `user_id` は書籍の登録者を表す入力であり、認証主体の証明には使わない。APIにWeb本人用Policyや認証由来の401・403を追加せず、実在しないIDは確定どおり422とする。Webから登録者を変更しない条件も維持する。

### Q-23：保存失敗・同時操作・障害時の扱い

**未回答（※仕様保留中）。** 保存結果と同時編集を以下に整理する。トランザクション・排他・ログの内部方式は開発側の案として検討する。

#### 保存失敗とロールバック（レビュー項目7）

**【課題・未決事項】**

書籍とジャンル関連の保存途中に失敗した場合の保存範囲、および入力検証後に発生したISBN重複・参照先消失を利用者へどう返すかが未確定。検証時に正常であっても、保存までに別操作で状態が変わり得る。

**【想定される影響・リスク（手戻りの大きさ）】**

書籍だけ保存されてジャンル集合が更新されないなど、利用者が送った一操作と保存結果が一致しなくなる。失敗を一律500にすると修正可能な入力を直せず、一律422にするとDB障害まで入力ミスとして扱う。保存の単位と例外の分類を揃えないと、Web・APIの共通保存処理を後から修正する必要がある。

**【開発側の推奨案（仮説）】**

| 場面 | 想定案（未承認） |
|---|---|
| 書籍とジャンルの保存途中に失敗 | 書籍項目とbook_genreの変更を1トランザクションで保存し、失敗時は当該操作の変更を全体として取り消す。成功応答を返さない |
| 検証後のISBN重複 | DB一意制約違反も通常のISBN重複エラーへ変換。Webは入力保持、APIは422。ほかのDB障害へ一律適用しない |
| 検証後の選択ジャンル消失 | 保存を取り消す。Webは元フォームへ入力保持してジャンル欄下にエラー、APIはgenresの該当入力キーにエラーを含む422。Q-19の不正ID文言で再選択を求める |
| 検証後のAPI参照ユーザー消失 | 保存を取り消し、user_idの項目別エラーを含む422。文言はQ-22の参照IDエラー案を使う |

部分保存を防いだうえで、原因を特定できる制約違反だけを通常の入力エラーへ戻す案を推奨する。ISBNの文言は確定済みの「そのISBNは既に使用されています。」を使い、DB接続障害等は下記の想定外障害として区別する。ジャンル削除のRESTRICT競合はQ-21の確定した削除不可結果を維持する。

#### 同時編集と上書き方針（レビュー項目6）

**【課題・未決事項】**

同じ書籍を開いた複数の編集が重なった場合に、後からの保存で上書きしてよいか、古い画面からの更新を検出して拒否するかが未確定。楽観的ロックの導入自体は決まっていない。

**【想定される影響・リスク（手戻りの大きさ）】**

後勝ちでは先に保存した編集内容が上書きされる。競合検出を追加する場合は、更新時点を渡す項目・比較処理・競合時の応答と再操作が必要になり、DB・Web・APIに波及する。トランザクションを使うだけでは、古い画面からの上書きを検出できない。

**【開発側の推奨案（仮説）】**

基本要件では楽観的ロックを導入せず、後から正常に保存された内容を採用する。項目ごとの自動マージはせず、書籍項目・ジャンル集合を一つの保存単位として整合させる。既存のDB・Blade・API契約に競合検出用のversion列・送信項目・409応答を追加せず、実装範囲を基本要件に収められるため、この案を推奨する。

編集中に対象書籍が削除された場合は確定どおり404とし、再作成しない。保存単位の整合性を保つ内部方式は開発側で検討する。後勝ちによる編集内容の上書きを許容するかは、実装前に回答を得る。

### Q-24：お気に入り解除後のページ補正

**未回答（※仕様保留中）。** レビュー項目8に対応。

**【課題・未決事項】**

お気に入り一覧で解除し、現在のページがなくなった場合の戻り先が未確定。Q-01の「操作元へ戻る」だけでは、消滅したページを維持するか補正するかは決まらない。

**【想定される影響・リスク（手戻りの大きさ）】**

現Bladeでは空のページに戻すと、全体に残件があっても「登録なし」となりページリンクも消える。11件ある状態で2ページ目の最後の1件を解除するだけで発生するため、通常の解除処理で戻り先を補正する必要がある。影響範囲は主にお気に入り一覧とリダイレクトのテストに限られる。

**【開発側の推奨案（仮説）】**

解除後は現在のページを維持し、そのページがなくなった場合だけ最後の有効なページへ戻す。11件の2ページ目の1件を解除した場合は1ページ目へ戻し、全件なくなった場合は1ページ目の既定の0件表示とする。残っているデータへ戻れるようにしつつ、不要な1ページ目への移動を避けられるため、この案を推奨する。

追加日時降順・10件／ページ・フラッシュなしを維持し、詳細からの操作は詳細へ戻す。既存Bladeは変更せず、バックエンドで戻り先を補正する。APIが明示指定された範囲外ページへ空配列を返すQ-22の案とは、目的を分けて扱う。

### Q-26：Seederの固定サンプルと個別実行

**未決・開発側方針の確認（※仕様保留中）。** レビュー項目9に対応。投入仕様の正本は [features.md](features.md#初期データ)、検証上の役割・追加データは [test_case.md](test_case.md#テストユーザーの役割) に従う。

**【課題・未決事項】**

UserSeeder・GenreSeeder・BookSeederの既指定値は確定しているが、書籍説明等の未指定文面を開発側で決めてよいかが未確定。レビューの本文・割当やお気に入り・いいねの具体的な組も保留されている。個別Seederの依存データがない場合と、既存DBで `User::first()` が山田太郎以外になる場合の処理も未確定。

**【想定される影響・リスク（手戻りの大きさ）】**

未指定のサンプル文面・配分まで承認待ちにすると、投入処理と画面確認用データの準備が止まる。毎回ランダムに変えると再現・比較が難しくなる。依存Seederの自動実行を個別クラスへ持たせると、意図しない投入や責務の重複も起こる。通常機能のDB・API契約への影響は小さいため、指定条件内の具体値・準備方法は開発裁量を明示して進めることを推奨する。

**【開発側の推奨案（仮説）】**

| 対象 | 推奨する方針（未承認） |
|---|---|
| UserSeeder | 指定の5名・email・共通パスワードを固定し、emailをキーにfirstOrCreate、新規時にHash::make('password')を使う。既存の名前・パスワードを上書きしない |
| GenreSeeder | 指定の10ジャンル名を固定し、nameをキーにfirstOrCreate。新しいジャンルや作成者項目を追加しない |
| BookSeeder | 指定11冊の項目・ジャンル・画像URLを維持。未指定のdescriptionはISBNごとに固定文面を開発側で用意し、乱数に依存させない。firstOrCreate・genres()->sync()と、既存書籍の項目・作成者を上書きしない条件を維持 |
| その他のサンプル | レビュー本文・32件の割当、お気に入り・いいねの具体的な組を、確定した件数・範囲内の固定一覧として開発側が用意する。ReviewSeederのcreate()、お気に入り・いいねのsyncWithoutDetaching()、Seederだけの本人いいね除外は維持 |
| 個別実行 | UserSeeder・GenreSeederはそれぞれ実行可能とし、BookSeederは利用者・指定ジャンルを先に準備してから実行する。依存Seederを自動で呼ばず、必要なUser::first()・指定ジャンルがなければ書籍投入前に理由を示して失敗させる |
| 登録者と既存DB | 新規DBでは指定順で利用者を作成し、User::first()が山田太郎となる。既存DBではUser::first()の結果をそのまま新規書籍の登録者に使い、山田へ固定するためのemail検索やID固定へ変更しない |
| 全体実行 | 通常はDatabaseSeederの既定順を使う。Review等の個別実行も依存データの事前準備を前提とし、途中失敗時は不足・失敗内容を明示する。全体の保存範囲・トランザクション方式は別途開発側で検討する |

固定一覧にすることで初回投入を再現しやすくし、依存関係の統括はDatabaseSeederへ集約する。初回件数と再実行後の累計は区別し、初期11冊へ別作成者の書籍や境界値用の追加データを混ぜない。開発裁量の範囲と既存DBの登録者の案を確認し、採用後に具体的なサンプル・実行前提をfeatures.mdへ記録する。
